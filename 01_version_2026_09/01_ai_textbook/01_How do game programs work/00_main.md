# 1장. 게임 프로그램은 어떻게 동작하는가

> 이 장의 질문: **게임은 아무도 키를 누르지 않아도 왜 계속 움직이는가?**

## 이 장에서 배우는 것

- 게임 루프(Game Loop)
- 입력 → 처리 → 상태 변경 → 렌더링
- 프레임과 시간, Delta Time
- `Update()`와 `Render()`를 나누는 이유
- 싱글플레이와 멀티플레이의 차이

---

## 1.1 보통 프로그램과 게임 프로그램

계산기 프로그램을 떠올려 봅시다.

```text
프로그램 시작
   ↓
사용자 입력을 기다림   ← 여기서 멈춰 있음
   ↓
계산
   ↓
결과 출력
   ↓
다시 입력을 기다림
```

계산기는 사용자가 아무것도 하지 않으면 **아무 일도 하지 않습니다.** 입력이 와야만 움직입니다.

게임은 다릅니다.

- 내가 가만히 있어도 몬스터는 걸어옵니다.
- 내가 가만히 있어도 시간이 흐르고, 총알이 날아가고, 화면이 바뀝니다.

즉 게임은 **입력을 기다리지 않고 계속 돌아가야 합니다.** 그래서 게임은 끝없이 반복하는 구조, **게임 루프**를 가집니다.

---

## 1.2 게임 루프

게임 루프의 가장 기본적인 모양은 다음과 같습니다.

```text
while (게임이 실행 중) {
    입력 처리 (Input)
    상태 갱신 (Update)
    화면 그리기 (Render)
}
```

이 반복 한 번을 **프레임(Frame)** 이라고 합니다.

```text
프레임 1: 입력 → 갱신 → 그리기
프레임 2: 입력 → 갱신 → 그리기
프레임 3: 입력 → 갱신 → 그리기
...
```

1초에 이 반복을 60번 하면 **60 FPS(Frames Per Second)** 입니다.

### 각 단계가 하는 일

| 단계 | 하는 일 | 예 |
| --- | --- | --- |
| Input | 지금 눌린 키, 마우스 상태를 읽는다 | "오른쪽 방향키가 눌려 있다" |
| Update | 규칙에 따라 게임 상태를 바꾼다 | "플레이어 x좌표를 1 늘린다" |
| Render | 현재 상태를 화면에 그린다 | "x=11 위치에 캐릭터를 그린다" |

### 중요한 함정: 입력을 "기다리면" 안 된다

계산기처럼 입력이 올 때까지 멈추면 어떻게 될까요?

```text
while (true) {
    key = 키가_눌릴_때까지_기다림()   ← 여기서 게임 전체가 멈춤
    Update()
    Render()
}
```

키를 누르지 않는 동안 몬스터도, 시간도, 화면도 전부 멈춥니다.

그래서 게임은 입력을 **기다리지 않고 확인만** 합니다.

```text
while (true) {
    if (키가_눌려_있는가()) { ... }   ← 눌려 있으면 처리, 아니면 그냥 지나감
    Update()
    Render()
}
```

> 이 "기다림(Blocking)" 문제는 5장에서 네트워크를 다룰 때 다시 나옵니다.
> 네트워크 데이터를 기다리느라 서버 전체가 멈추는 문제와 같은 구조입니다.

## 1.3 게임 상태(Game State)

Update와 Render 사이에는 **게임 상태**가 있습니다.

게임 상태란 **"지금 이 순간 게임 세계가 어떤 모습인가"를 나타내는 데이터 전부**입니다.

```text
Game State
 ├─ Player
 │   ├─ x = 10
 │   ├─ y = 5
 │   └─ hp = 100
 ├─ Monster
 │   ├─ x = 20
 │   └─ y = 5
 └─ 경과 시간 = 12.4초
```

- **Update**는 상태를 **바꾸는** 쪽입니다.
- **Render**는 상태를 **읽기만 하는** 쪽입니다.

```text
Input ──→ Update ──(쓰기)──→ [ Game State ] ──(읽기)──→ Render
```

이 그림이 이 교과서 전체에서 가장 중요한 그림 중 하나입니다.
나중에 멀티플레이에서는 **"이 Game State는 누구의 컴퓨터에 있는가?"** 가 핵심 질문이 됩니다.

---

## 1.4 `Update()`와 `Render()`를 나누는 이유

한 함수에서 전부 해도 게임은 돌아갑니다.

```text
// 나쁜 예
function Frame() {
    if (오른쪽키) {
        player.x += 1
        화면에_그리기(player)     ← 이동과 그리기가 섞여 있음
    }
}
```

그런데 이렇게 섞으면 문제가 생깁니다.

1. **그리기를 끄면 게임도 멈춘다.** 화면을 안 그리고 싶을 때(예: 창 최소화) 게임 로직까지 같이 멈춥니다.
2. **그리는 속도와 게임 속도가 묶인다.** 화면을 느리게 그리는 컴퓨터에서는 게임도 느려집니다.
3. **서버를 만들 수 없다.** ← 이게 가장 중요합니다.

### 서버에는 화면이 없다

게임 서버는 화면을 그리지 않습니다. 서버가 하는 일은 **Update뿐**입니다.

```text
클라이언트:  Input → Update → Render
서버:                Update
```

Update와 Render가 처음부터 나뉘어 있어야, 나중에 Update 부분만 떼어서 서버로 옮길 수 있습니다.
2장에서 바로 이 작업을 합니다.

```text
// 좋은 예
function Update() {
    if (오른쪽키) player.x += 1     ← 상태만 바꿈
}

function Render() {
    화면에_그리기(player)            ← 상태를 읽어서 그리기만 함
}
```

## 1.5 프레임과 시간: Delta Time

### 문제: 컴퓨터마다 속도가 다르다

"한 프레임마다 1칸 이동"하도록 만들었다고 해 봅시다.

| 컴퓨터 | FPS | 1초에 이동한 거리 |
| --- | --- | --- |
| 빠른 컴퓨터 | 60 | 60칸 |
| 느린 컴퓨터 | 30 | 30칸 |

같은 게임인데 **빠른 컴퓨터에서 캐릭터가 두 배 빠릅니다.** 멀티플레이라면 불공평한 게임이 됩니다.

### 해결: 프레임이 아니라 시간 기준으로 움직인다

지난 프레임에서 이번 프레임까지 걸린 시간을 **Delta Time(dt)** 이라고 합니다.

```text
60 FPS → dt ≈ 1/60초 ≈ 0.0167초
30 FPS → dt ≈ 1/30초 ≈ 0.0333초
```

이동을 "칸/프레임"이 아니라 "칸/초"로 정하고, dt를 곱합니다.

```text
speed = 5          // 1초에 5칸

function Update(dt) {
    if (오른쪽키) player.x += speed * dt
}
```

| 컴퓨터 | 1프레임 이동 | 1초 동안 프레임 수 | 1초에 이동한 거리 |
| --- | --- | --- | --- |
| 60 FPS | 5 × 0.0167 ≈ 0.083칸 | 60 | 5칸 |
| 30 FPS | 5 × 0.0333 ≈ 0.167칸 | 30 | 5칸 |

이제 FPS가 달라도 **1초에 움직이는 거리는 같습니다.**

### dt를 포함한 게임 루프

```text
lastTime = 현재시간()

while (게임이 실행 중) {
    now = 현재시간()
    dt  = now - lastTime
    lastTime = now

    Input()
    Update(dt)
    Render()
}
```

> dt 방식에도 약점이 있습니다. dt가 갑자기 크게 튀면(예: 컴퓨터가 잠깐 멈춤) 캐릭터가 벽을 뚫고 지나갈 수도 있습니다.
> 그래서 서버는 보통 **고정된 간격(Fixed Tick)** 으로 Update를 돌립니다. 이 내용은 10장에서 다룹니다.

## 1.6 싱글플레이와 멀티플레이

지금까지 만든 구조는 **한 컴퓨터 안에서 전부** 일어납니다.

```text
[ 내 컴퓨터 ]
Input → Update → Game State → Render
```

이것이 싱글플레이입니다. 게임 상태가 **하나**이고, 그 상태를 보는 사람도 **한 명**입니다.

멀티플레이가 되면 질문이 생깁니다.

```text
[ A의 컴퓨터 ]              [ B의 컴퓨터 ]
Input → Update → State?     Input → Update → State?
```

- A의 화면과 B의 화면에 보이는 세계는 같아야 합니다.
- 그런데 Game State가 두 컴퓨터에 따로 있으면, 둘이 달라질 수 있습니다.
- A가 "나는 몬스터를 잡았다"고 하고 B는 "몬스터가 아직 살아 있다"고 하면, **누구 말이 맞을까요?**

이 질문에 대한 답이 **서버**입니다.

```text
[ A ]  Input ─┐                  ┌─→ Render [ A ]
              ├─→ [ 서버: Update + 진짜 Game State ] ─┤
[ B ]  Input ─┘                  └─→ Render [ B ]
```

2장에서 이 구조를 직접 만들어 봅니다.

## 예제 1 — 미니 게임 루프

> AI 예제 위치: `02_ai_example`
> 내 구현 위치: `03_human_example`

### 요구사항

콘솔(터미널)에서 동작하는 아주 작은 게임을 만듭니다.

1. 가로 20칸, 세로 10칸짜리 맵을 그린다.
2. 플레이어는 `@`로 표시한다.
3. 방향키 또는 WASD로 플레이어를 움직인다.
4. 플레이어는 맵 밖으로 나갈 수 없다.
5. 화면 위쪽에 현재 FPS와 플레이어 좌표를 표시한다.
6. `Q`를 누르면 종료한다.

```text
FPS: 60  Pos: (4.0, 2.0)
+--------------------+
|                    |
|                    |
|    @               |
|                    |
|                    |
+--------------------+
```

### 구조 조건

- `Input()`, `Update(dt)`, `Render()`를 **반드시 별도 함수**로 만든다.
- 게임 상태는 **하나의 구조체(또는 클래스)** 에 모은다.
- `Render()`는 게임 상태를 **읽기만** 하고 절대 바꾸지 않는다.
- 이동 속도는 "초당 칸 수"로 정하고 `dt`를 사용한다.
- 입력은 **기다리지 않는다**(Non-blocking).

### 언어

아무 언어나 괜찮습니다. 콘솔에서 키 입력을 기다리지 않고 읽는 방법만 찾으면 됩니다.

## 직접 구현 순서

코드를 보기 전에 아래 순서대로 직접 만들어 봅니다.

1. **빈 루프**: 무한 반복하면서 프레임 수만 세서 출력한다.
2. **FPS 제한**: 1초에 60번만 돌도록 쉬는 시간을 넣는다.
3. **Game State**: 플레이어 좌표를 담는 구조체를 만든다.
4. **Render**: 상태를 읽어 맵과 `@`를 그린다.
5. **Input**: 키를 기다리지 않고 읽는다.
6. **Update**: 입력에 따라 좌표를 바꾼다. 처음에는 dt 없이 만든다.
7. **Delta Time**: dt를 적용한다.

막히면 AI에게 **"코드는 주지 말고, 무엇을 찾아보면 되는지만 알려줘"** 라고 물어봅니다.

## 고장 내기

완성한 게임에 일부러 문제를 만들어 봅니다.

| 실험 | 방법 | 관찰할 것 |
| --- | --- | --- |
| 1-1 | dt를 **빼고** FPS를 60 → 10으로 바꾼다 | 캐릭터 속도가 어떻게 변하는가? |
| 1-2 | dt를 **넣고** FPS를 60 → 10으로 바꾼다 | 속도는 같은가? 움직임은 어떻게 보이는가? |
| 1-3 | 입력을 **기다리는(Blocking)** 방식으로 바꾼다 | 키를 안 누르면 FPS 표시는 어떻게 되는가? |
| 1-4 | `Update()` 안에 0.5초 멈추는 코드를 넣는다 | dt가 커지면 캐릭터는 어떻게 움직이는가? |
| 1-5 | `Render()`를 호출하지 않는다 | 게임 상태는 계속 바뀌는가? (좌표를 로그로 확인) |

실험 1-5는 특히 중요합니다. **화면이 없어도 게임은 돌아간다**는 것, 즉 서버가 가능하다는 것을 확인하는 실험입니다.

6. 두 사람이 각자의 컴퓨터에 게임 상태를 따로 가지고 있으면 어떤 문제가 생기는가?

## 이 장의 핵심 정리

```text
1. 게임은 입력을 기다리지 않고 계속 도는 루프다.
2. 루프 한 번 = 프레임 = Input → Update → Render
3. Update는 게임 상태를 바꾸고, Render는 읽기만 한다.
4. 이동은 프레임이 아니라 시간(dt) 기준으로 계산한다.
5. Update와 Render가 나뉘어 있어야 Update만 서버로 옮길 수 있다.
```
