# 게임 클라이언트·서버 구조 교과서 — 목차

> 작성일: 2026-09-23
> 목적: 게임 클라이언트 및 서버 구조를 이해하기 위한 학습 자료

## 이 교과서의 중심 질문

1. 게임 상태는 **어디에서** 결정되는가?
2. 클라이언트와 서버는 **무엇을** 주고받는가?
3. 네트워크가 **망가지면** 무슨 일이 생기고, 어떻게 대처하는가?
4. 클라이언트를 **믿으면 안 되는** 이유는 무엇인가?

최종 목표는 **"플레이어가 클릭했을 때 실제로 무슨 일이 일어나는가"를 패킷 단위로 추적하고 설명할 수 있는 것**입니다.

```text
입력 → 명령 → 직렬화 → 네트워크 → 서버 수신 → 역직렬화 → 검증
     → 게임 로직 → 상태 변경 → 스냅샷/이벤트 → 네트워크 → 클라이언트 상태 갱신 → 렌더링
```

## 각 장의 구성

모든 장은 아래 순서를 따릅니다.

| 항목 | 내용 |
| --- | --- |
| 개념 | 이 장에서 배우는 것 |
| 예제 | AI가 만든 예제 프로그램 (`02_ai_example`) |

| 고장 내기 | 일부러 장애나 악성 입력을 넣어 보기 (해당 장만) |

특정 엔진이나 언어에 묶이지 않도록 합니다. Unity나 Unreal 같은 큰 엔진은 쓰지 않고, 콘솔이나 간단한 2D 화면으로 진행합니다.

## Part 1. 기본 개념

### 1장. 게임 프로그램은 어떻게 동작하는가
- 게임 루프: 입력 → 처리 → 상태 변경 → 렌더링
- 프레임과 시간, Delta Time
- `Update()`와 `Render()`의 분리
- 싱글플레이와 멀티플레이의 차이

**예제 1 — 미니 게임 루프**: 키보드로 플레이어를 움직이고 화면에 출력하기
**목표**: 게임 프로그램의 기본 실행 흐름을 설명할 수 있다.

### 2장. 클라이언트와 서버는 왜 분리하는가
- 클라이언트의 책임 / 서버의 책임
- 게임 상태(Game State)
- 권위(Authority)의 개념
- 클라이언트가 모든 것을 결정하면 생기는 문제

**예제 2 — 싱글플레이 게임을 클라이언트/서버로 나누기** (같은 프로세스 안에서 Request/Response로 분리)
**목표**: "화면을 보여주는 것"과 "실제 상태를 결정하는 것"을 구분할 수 있다.

## Part 4. 동기화의 기초

### 8장. 플레이어 이동 동기화
- 입력 전송과 위치 전송의 차이
- 서버 상태와 클라이언트 상태
- Broadcast

**예제 8 — 2인용 이동 게임**: 두 명이 접속하고, 서버가 위치를 관리하고, 서로의 캐릭터가 보인다.
**목표**: "내 캐릭터를 움직이는 것"과 "남에게 내 움직임을 보여주는 것"이 다른 문제임을 이해한다.

### 9장. 서버 권위(Server Authority)
- Server Authority와 Client Authority
- 클라이언트는 "의도"를 보내고 서버가 "결과"를 정한다
- 검증(Validation): 살아 있는가, 대상이 있는가, 거리는 되는가, 쿨다운이 끝났는가
- 서버가 계산할 것 / 클라이언트가 계산해도 되는 것

**예제 9 — 서버 권위 이동과 공격**
**목표**: 클라이언트가 보낸 값을 그대로 믿으면 안 되는 이유를 설명할 수 있다.

### 10장. Tick과 게임 시간
- Tick, Fixed Update, Server Time
- Frame Rate와 Tick Rate
- 게임 로직 주기와 렌더링 주기의 분리

**예제 10 — 20 TPS 게임 서버**
**고장 내기**: 클라이언트 FPS 낮추기, 서버 Tick을 60 → 20 → 10으로 낮추기
**목표**: 서버가 일정한 간격으로 세계를 처리하는 이유를 설명할 수 있다.

## Part 5. 네트워크를 망가뜨려 보기

이 파트는 **문제를 먼저 겪고, 해결 기술은 나중에 배우는** 순서로 진행합니다.

### 11장. 네트워크 장애 시뮬레이터
- 게임 코드를 고치지 않고 네트워크 환경만 바꾸는 구조
- 옵션: `--latency`, `--packet-loss`, `--jitter`, `--reorder`
- 실험 기록 남기는 법 (부록 B)

**예제 11 — 클라이언트와 서버 사이에 끼우는 장애 시뮬레이터**

| 실험 | 넣는 장애 | 관찰할 것 |
| --- | --- | --- |
| 11-1 | 지연 100ms | Latency |
| 11-2 | 지연 300ms | 체감 지연 |
| 11-3 | 패킷 5% 유실 | 유실과 재전송 |
| 11-4 | 패킷 순서 뒤바꿈 | Sequence Number의 필요성 |
| 11-5 | 지연시간이 계속 변함 | Jitter |

**목표**: 서버에 있는 위치와 화면에 보이는 위치가 항상 같지는 않다는 것을 직접 확인한다.

### 12장. Snapshot과 Interpolation
- Snapshot
- Interpolation / Extrapolation
- 보간 버퍼와 일부러 늦게 그리기

**예제 12 — 다른 플레이어의 움직임을 부드럽게 보이게 하기**
**목표**: 다른 플레이어가 끊겨 보이는 이유와 해결 방법을 설명할 수 있다.

### 13장. Client Prediction과 Server Reconciliation
- 입력 즉시 반영하기 (Prediction)
- 서버 결과로 되돌리고 다시 적용하기 (Reconciliation)
- 입력 번호와 확인 응답(Ack)

**예제 13 — 200ms 지연에서도 내 캐릭터가 바로 움직이는 게임**
**고장 내기**: Prediction을 켠 상태에서 패킷 10% 유실 넣기
**목표**: 내 캐릭터가 순간적으로 되돌아가는 현상의 원인과 해결 방법을 설명할 수 있다.

### 14장. Lag Compensation
- "내 화면에서는 맞았는데 서버에서는 빗나감" 문제
- 과거 시점의 상태로 되감아 판정하기
- 공정성의 한계

**예제 14 — 지연이 있는 상태에서 공격 판정하기**
**목표**: 지연 보정이 누구에게 유리하고 누구에게 불리한지 설명할 수 있다.

## Part 6. 악성 클라이언트 실험

모든 실험은 **내가 만든 로컬 테스트 게임에서만** 진행합니다.

### 15장. 클라이언트는 믿을 수 없다
- 클라이언트가 보내는 패킷을 직접 만들어 보기
- 값을 믿는 서버(Server A)와 검증하는 서버(Server B) 비교

**예제 15 — 같은 악성 클라이언트를 Server A와 Server B에 연결하기**

| 공격 실험 | 서버 설계가 잘못되었을 때 |
| --- | --- |
| 이동 속도 조작 | 순간이동 |
| 공격 속도 조작 | 비정상적인 연사 |
| 데미지 값 조작 | 비정상적인 피해 |
| 아이템 획득 메시지 위조 | 아이템 무단 획득 |
| 존재하지 않는 행동 요청 | 게임 상태 변조 |
| 오래된 패킷 재전송 (Replay) | 같은 행동 반복 |
| 패킷 순서 조작 | 상태 꼬임 |
| 요청 폭주 | 서버 부하 |

**목표**: 보안의 핵심이 패킷 암호화가 아니라 **서버의 권한 구조와 검증 로직**이라는 것을 설명할 수 있다.

### 16장. 검증 로직 설계
- 요청마다 무엇을 검사할지 표로 정리하기
- 속도, 쿨다운, 범위, 소유권 검사
- 요청 빈도 제한(Rate Limit)
- 수상한 행동 로그 남기기

**예제 16 — 15장의 공격을 모두 막는 Server B 완성하기**
**목표**: 새 기능을 추가할 때 서버가 검증해야 할 항목을 스스로 뽑을 수 있다.
