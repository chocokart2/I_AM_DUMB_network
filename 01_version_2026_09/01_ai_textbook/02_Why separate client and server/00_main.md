# 2장. 클라이언트와 서버는 왜 분리하는가

> 이 장의 질문: **두 사람이 같은 게임을 할 때, "진짜" 게임 세계는 어디에 있는가?**

## 이 장에서 배우는 것

- 게임 상태(Game State)를 다시 보기: 진짜 상태와 보여주기용 사본
- 권위(Authority)의 개념
- 클라이언트의 책임 / 서버의 책임
- 클라이언트가 모든 것을 결정하면 생기는 문제
- 결과가 아니라 의도를 보낸다: Request / Response

---

## 2.1 1장 복습: 모든 것이 한 곳에 있었다

1장에서 만든 게임은 이런 모양이었습니다.

```text
[ 내 컴퓨터, 프로그램 하나 ]

Input ──→ Update ──(쓰기)──→ [ Game State ] ──(읽기)──→ Render
```

입력을 받는 것도, 규칙을 적용하는 것도, 상태를 저장하는 것도, 화면을 그리는 것도 **전부 한 프로그램 안**에서 일어납니다.

싱글플레이에서는 이게 전혀 문제가 되지 않습니다. 게임 상태를 보는 사람이 **나 한 명뿐**이기 때문입니다.

1장 마지막에서 이런 질문을 남겼습니다.

> A가 "나는 몬스터를 잡았다"고 하고 B는 "몬스터가 아직 살아 있다"고 하면, **누구 말이 맞을까요?**

이 장은 이 질문에 답하는 장입니다.

---

## 2.2 두 사람이 같은 세계를 보려면

A와 B가 같은 맵에서 같은 몬스터를 보고 있다고 해 봅시다.
1장 구조를 그대로 두 컴퓨터에 복사하면 이렇게 됩니다.

```text
[ A의 컴퓨터 ]                        [ B의 컴퓨터 ]
Input → Update → [ State A ] → Render   Input → Update → [ State B ] → Render
                  몬스터 HP = 0                           몬스터 HP = 30
```

게임 상태가 **두 개** 생겼습니다. 그리고 두 상태는 서로 다를 수 있습니다.

- A의 컴퓨터에서는 몬스터가 죽었습니다.
- B의 컴퓨터에서는 몬스터가 아직 살아 있습니다.
- 둘 다 "내 컴퓨터에 있는 게 맞다"고 주장할 수 있습니다.

이 상황을 해결하는 가장 단순한 방법은 이것입니다.

> **진짜 게임 상태는 딱 하나만 둔다. 그리고 그것을 한 곳에서만 바꾼다.**

그 "한 곳"이 **서버**입니다.

```text
          [ 서버 ]
     [ 진짜 Game State ]
       ↑            ↓
    요청 │            │ 결과
       │            ↓
[ A ]                [ B ]
보여주기용 사본         보여주기용 사본
```

A와 B의 컴퓨터(클라이언트)에도 상태가 있긴 합니다. 화면을 그려야 하니까요.
하지만 그것은 **서버의 상태를 받아서 복사해 둔 사본**입니다. 진짜는 서버에 있습니다.

### 진짜 상태와 사본

| | 진짜 상태 (서버) | 사본 (클라이언트) |
| --- | --- | --- |
| 개수 | 하나 | 클라이언트 수만큼 |
| 누가 바꾸는가 | 서버의 Update | 서버가 보낸 결과로만 갱신 |
| 용도 | 게임 결과를 결정 | 화면에 그리기 |
| 틀릴 수 있는가 | 정의상 "맞는 것" | 오래됐거나 다를 수 있음 |

> 마지막 줄이 중요합니다. **클라이언트 화면에 보이는 것은 항상 "조금 전의 서버 상태"** 입니다.
> 네트워크로 전달되는 데 시간이 걸리기 때문입니다. 이 차이는 11~14장 전체의 주제가 됩니다.

---

## 2.3 권위(Authority)

어떤 값에 대해 **"최종 결정권을 가진 쪽"** 을 그 값의 **권위(Authority)** 를 가진다고 말합니다.

- 플레이어 위치의 권위가 서버에 있다 → 클라이언트가 뭐라고 하든, 위치는 서버가 정한다.
- 플레이어 위치의 권위가 클라이언트에 있다 → 클라이언트가 "나 여기 있어"라고 하면 그게 위치가 된다.

서버가 게임 상태의 권위를 가지는 방식을 **서버 권위(Server Authoritative)** 방식이라고 합니다. [1][2]

```text
클라이언트: "오른쪽으로 가고 싶어요"       ← 요청 (결정권 없음)
서버:      "벽이 없으니 x = 11 입니다"     ← 결과 (결정권 있음)
```

### 권위는 값마다 다르게 줄 수 있다

모든 것을 서버가 결정해야 하는 것은 아닙니다. 게임 결과에 영향이 없는 것은 클라이언트가 정해도 됩니다.

| 값 | 권위 | 이유 |
| --- | --- | --- |
| 플레이어 위치 | 서버 | 조작하면 순간이동이 된다 |
| HP, 데미지 | 서버 | 조작하면 무적이 된다 |
| 아이템 획득 | 서버 | 조작하면 아이템을 복사할 수 있다 |
| 카메라 각도 | 클라이언트 | 나만 보는 화면이다 |
| UI 창 위치, 옵션 | 클라이언트 | 게임 결과와 상관없다 |
| 피격 이펙트, 파티클 | 클라이언트 | 보여주기만 하는 것이다 |

기준은 하나입니다.

> **이 값을 플레이어가 마음대로 바꿨을 때, 다른 플레이어가 피해를 보는가?**
> 그렇다면 서버가 권위를 가져야 합니다.

### "서버"는 역할이다

서버라고 하면 데이터 센터의 큰 컴퓨터를 떠올리기 쉽지만, 서버는 **역할**입니다.

- **전용 서버(Dedicated Server)**: 서버 역할만 하는 프로그램이 따로 돈다. 화면도 입력도 없다.
- **리슨 서버(Listen Server)**: 플레이어 중 한 명의 게임이 서버 역할도 같이 한다. 친구끼리 "방 만들기"를 하는 경우가 흔히 이렇다.

어느 쪽이든 **진짜 상태를 하나 두고, 그것을 서버 역할이 바꾼다**는 구조는 같습니다.
이 교과서에서는 이해하기 쉬운 전용 서버를 기준으로 설명합니다.

> 서버를 두지 않고 모든 참가자가 같은 입력을 받아 똑같이 계산하는 방식(Peer-to-Peer Lockstep)도 있습니다. [3]
> 주로 RTS 같은 장르에서 쓰였는데, 이 교과서의 범위 밖이므로 이름만 알아 둡니다.

## 2.4 클라이언트의 책임 / 서버의 책임

1장의 `Input → Update → Render`를 둘로 나누면 이렇게 됩니다.

```text
[ 클라이언트 ]                               [ 서버 ]
Input  ──(요청: "오른쪽으로 가고 싶다")──→   요청 받기
                                             검증 (벽인가? 살아 있나?)
                                             Update  ──→ [ 진짜 Game State ]
사본 갱신 ←──(결과: "x = 11")────────────── 결과 보내기
Render
```

| | 클라이언트 | 서버 |
| --- | --- | --- |
| 하는 일 | 입력 받기, 요청 보내기, 결과 받기, 화면 그리기 | 요청 받기, 검증, 게임 규칙 적용, 결과 보내기 |
| 게임 상태 | 사본 | 진짜 |
| 화면 | 있음 | 없음 |
| 입력 장치 | 있음 | 없음 |
| 누구의 손에 있는가 | **플레이어** | **게임 운영자** |

마지막 줄이 이 장에서 가장 중요한 줄입니다.

### 클라이언트는 플레이어의 컴퓨터에서 돈다

클라이언트 프로그램은 플레이어의 컴퓨터에 설치됩니다. 그 말은 플레이어가

- 메모리 값을 바꿀 수 있고,
- 프로그램을 수정할 수 있고,
- 아예 **클라이언트를 흉내 내는 다른 프로그램**을 만들어서 서버에 접속할 수도 있다는 뜻입니다.

즉 **서버 입장에서 클라이언트가 보낸 데이터는 "누가 보냈는지 모르는 데이터"** 입니다. [1]
진짜 게임 클라이언트가 보냈을 수도 있고, 조작된 프로그램이 보냈을 수도 있습니다. 서버는 구분할 수 없습니다.

반면 서버는 운영자의 컴퓨터에서 돌기 때문에 플레이어가 건드릴 수 없습니다.
그래서 **결정은 건드릴 수 없는 쪽(서버)이 해야** 합니다.

## 2.5 클라이언트가 모든 것을 결정하면 생기는 문제

"그냥 각 클라이언트가 자기 상태를 계산하고, 서버는 그걸 다른 사람에게 전달만 하면 되지 않나?"라고 생각할 수 있습니다.
이런 서버를 **중계만 하는 서버**라고 해 봅시다.

```text
[ A ] "내 위치는 x=11" ──→ [ 서버: 받은 걸 그대로 전달 ] ──→ [ B ]
```

만들기는 아주 쉽습니다. 서버에 게임 규칙이 하나도 없으니까요. 하지만 문제가 생깁니다.

### 문제 1. 조작이 그대로 통한다

| 클라이언트가 보낸 것 | 중계 서버의 반응 | 결과 |
| --- | --- | --- |
| "내 위치는 x=9999" | 그대로 전달 | 순간이동 |
| "내 HP는 99999" | 그대로 전달 | 무적 |
| "몬스터에게 데미지 99999" | 그대로 전달 | 한 방에 처치 |
| "전설 아이템을 주웠다" | 그대로 전달 | 없는 아이템이 생김 |

서버에 규칙이 없으니, 이 값이 말이 되는지 **판단할 방법 자체가 없습니다.**

### 문제 2. 두 사람의 말이 부딪힌다

바닥에 아이템이 하나 있고, A와 B가 거의 동시에 줍기를 눌렀습니다.

```text
A의 컴퓨터: "아이템 없음 → 내가 주웠다"
B의 컴퓨터: "아이템 없음 → 내가 주웠다"
```

각자 자기 컴퓨터에서 먼저 처리했으니 **둘 다 주웠습니다.** 아이템이 하나에서 둘이 됐습니다.
누가 먼저인지 정해 줄 **하나의 기준**이 없기 때문입니다.

서버 권위 방식이라면 이렇게 됩니다.

```text
서버: A의 요청이 먼저 도착 → A에게 줌, 아이템 제거
서버: B의 요청 도착 → 아이템이 이미 없음 → 거절
```

> 서버 안에서도 "동시에" 처리하면 같은 문제가 생길 수 있습니다. 이건 22장(동시성)에서 다룹니다.

### 문제 3. 상태가 조금씩 어긋난다

조작하지 않아도 문제가 생깁니다. A와 B가 똑같은 코드로 계산해도,

- 소수점 계산 결과가 컴퓨터마다 미세하게 다를 수 있고 [3]
- 메시지가 늦게 도착하거나 안 도착할 수 있습니다.

작은 차이가 쌓이면 A의 화면과 B의 화면이 점점 달라집니다. 그리고 **어느 쪽이 맞는지 정할 기준이 없습니다.**

서버 권위 방식에서는 기준이 있습니다. **서버의 상태가 맞는 것**입니다. 클라이언트가 어긋나면 서버 상태로 다시 맞추면 됩니다.

### 정리

| 문제 | 원인 | 서버 권위 방식에서 |
| --- | --- | --- |
| 조작 | 클라이언트가 결과를 정한다 | 서버가 검증하고 결과를 정한다 |
| 충돌 | 판단하는 곳이 여러 곳이다 | 판단하는 곳이 한 곳이다 |
| 어긋남 | 기준이 되는 상태가 없다 | 서버 상태가 기준이다 |

## 2.6 결과가 아니라 의도를 보낸다

그렇다면 클라이언트는 서버에 **무엇을** 보내야 할까요?

```text
나쁜 예:  클라이언트 → 서버: "내 위치는 x = 11"          ← 결과
좋은 예:  클라이언트 → 서버: "오른쪽으로 가고 싶다"       ← 의도(요청)
```

결과를 보내면 서버는 그 값이 맞는지 다시 계산해 봐야 합니다. 어차피 다시 계산할 거라면 처음부터 **의도만** 받고 서버가 계산하는 것이 단순합니다. [1][2]

| 의도 (클라이언트가 보냄) | 서버가 확인할 것 | 결과 (서버가 정함) |
| --- | --- | --- |
| "오른쪽으로 가고 싶다" | 벽이 있는가? 살아 있는가? | 새 위치 |
| "저 몬스터를 공격하고 싶다" | 몬스터가 있는가? 거리가 되는가? 쿨다운은? | 데미지, 남은 HP |
| "저 아이템을 줍고 싶다" | 아이템이 아직 있는가? 가까운가? 가방에 자리가 있는가? | 획득 성공/실패 |

> 이 "확인할 것" 목록이 **검증(Validation)** 입니다. 9장과 16장에서 본격적으로 다룹니다.

## 2.7 Request / Response

클라이언트와 서버가 주고받는 데이터를 **메시지(Message)** 라고 부르겠습니다.

- 클라이언트 → 서버: **요청(Request)**. "이걸 하고 싶다."
- 서버 → 클라이언트: **응답(Response)**. "결과는 이렇다."

```text
// 요청
MoveRequest {
    dx = +1      // 오른쪽
    dy =  0
}

// 응답
StateResponse {
    x = 11
    y = 5
}
```

### 네트워크 없이 먼저 나눠 본다

이 장에서는 아직 네트워크를 쓰지 않습니다. **한 프로그램 안에서** 클라이언트와 서버를 나눕니다.

"한 프로그램 안이면 그냥 함수 호출하면 되지, 왜 메시지를 만드나요?"

한 프로그램 안에서는 클라이언트 코드가 서버의 게임 상태를 **직접 건드릴 수 있습니다.**

```text
// 한 프로그램 안이라서 가능하지만, 절대 하면 안 되는 것
client.Update() {
    server.state.player.x += 1     ← 클라이언트가 진짜 상태를 직접 바꿈
}
```

이렇게 짜 두면 나중에 서버를 다른 컴퓨터로 옮길 때 이 코드는 전부 동작하지 않습니다.
다른 컴퓨터에 있는 변수는 직접 건드릴 수 없고, **메시지를 보내는 것밖에 할 수 없기 때문**입니다.

그래서 처음부터 규칙을 정합니다.

> **클라이언트와 서버는 서로의 변수를 직접 건드리지 않는다. 메시지로만 대화한다.**

이 규칙만 지키면, 3장에서 "메시지를 전달하는 통로"만 네트워크로 바꾸면 됩니다.

```text
2장:  클라이언트 ──[ 메모리 안의 큐 ]──→ 서버
3장:  클라이언트 ──[ 네트워크(Socket) ]──→ 서버
```

### 메시지 큐(Queue)

"메모리 안의 통로"로는 **큐(Queue)** 를 씁니다. 먼저 넣은 것이 먼저 나오는 줄입니다.

```text
toServer 큐:  클라이언트가 넣고, 서버가 꺼낸다
toClient 큐:  서버가 넣고, 클라이언트가 꺼낸다
```

함수를 바로 호출하는 대신 큐를 쓰는 이유는, 네트워크와 성질이 비슷하기 때문입니다.

- 보내는 쪽은 넣고 **바로 다음 일을 한다.** 상대가 처리할 때까지 기다리지 않는다.
- 받는 쪽은 **자기 차례가 됐을 때** 쌓여 있는 것을 꺼내서 처리한다.

> 1장에서 "입력을 기다리면 게임이 멈춘다"고 했습니다. 서버의 응답을 기다리는 것도 똑같습니다.
> 클라이언트는 응답을 **기다리지 않고**, 도착해 있으면 처리하고 없으면 그냥 지나갑니다.

### 한 프레임의 흐름

같은 프로그램 안에서 한 루프가 클라이언트와 서버를 번갈아 돌립니다.

```text
while (실행 중) {
    // --- 클라이언트 ---
    client.Input()              // 키를 읽고, 요청을 toServer 큐에 넣는다

    // --- 서버 ---
    server.ReceiveRequests()    // toServer 큐에서 요청을 꺼낸다
    server.Update(dt)           // 검증하고 진짜 상태를 바꾼다
    server.SendState()          // 결과를 toClient 큐에 넣는다

    // --- 클라이언트 ---
    client.ReceiveResponses()   // toClient 큐에서 결과를 꺼내 사본을 갱신한다
    client.Render()             // 사본을 읽어 그린다
}
```

1장과 비교해 보세요.

| 1장 | 2장 |
| --- | --- |
| `Input()` | `client.Input()` → 요청 생성 |
| `Update(dt)` | `server.Update(dt)` — **서버로 이사감** |
| `Render()` | `client.Render()` — 사본을 읽음 |
| Game State 하나 | 진짜(서버) + 사본(클라이언트) |

1장에서 Update와 Render를 나눠 둔 덕분에, Update만 떼어서 서버로 옮길 수 있었습니다.

### 이 구조의 대가: 반응이 늦어진다

지금은 한 프로그램 안이라 요청과 응답이 같은 프레임에 끝납니다.
하지만 서버가 멀리 있으면 이렇게 됩니다.

```text
0ms    키 누름 → 요청 보냄
50ms   서버 도착 → 처리
100ms  응답 도착 → 화면에 반영
```

**키를 누르고 0.1초 뒤에야 캐릭터가 움직입니다.** 서버 권위 방식을 쓰면 반드시 생기는 문제입니다. [1]
해결 방법(Client Prediction)은 13장에서 배웁니다. 이 장의 "고장 내기"에서 먼저 이 느낌을 겪어 봅니다.

## 예제 2 — 싱글플레이 게임을 클라이언트/서버로 나누기

> AI 예제 위치: `02_ai_example`
> 내 구현 위치: `03_human_example`

### 요구사항

1장의 미니 게임 루프를 **같은 프로그램 안에서** 클라이언트와 서버로 나눕니다.
게임 화면과 조작은 1장과 똑같아야 합니다.

1. 가로 20칸, 세로 10칸짜리 맵, 플레이어는 `@`.
2. 방향키 또는 WASD로 이동, `Q`로 종료.
3. 맵 가운데 어딘가에 벽(`#`)을 몇 칸 둔다. 플레이어는 벽과 맵 밖으로 나갈 수 없다.
4. 화면 위쪽에 FPS, **서버 좌표**, **클라이언트 사본 좌표**를 따로 표시한다.

```text
FPS: 60  Server: (4.0, 2.0)  Client: (4.0, 2.0)
+--------------------+
|                    |
|         #          |
|    @    #          |
|         #          |
|                    |
+--------------------+
```

### 구조 조건

- `Client`와 `Server`를 **별도 클래스(또는 모듈)** 로 만든다.
- 진짜 게임 상태는 **`Server` 안에만** 있다. `Client`는 `Server`의 상태에 접근할 수 없다.
- `Client`와 `Server`는 **메시지 큐 두 개(`toServer`, `toClient`)로만** 대화한다.
  - `Client`가 `Server`의 함수를 직접 호출하거나, `Server`가 `Client`의 함수를 직접 호출하지 않는다.
- 메시지는 **순수한 데이터**(숫자, 문자열 등)만 담는다. 객체의 참조나 포인터를 담지 않는다.
  - 3장에서 메시지를 네트워크로 보내려면 바이트로 바꿀 수 있어야 하기 때문이다.
- 클라이언트는 **위치가 아니라 이동 의도(방향)** 를 보낸다.
- 벽과 맵 경계 검사는 **서버만** 한다. 클라이언트에는 충돌 검사 코드가 없다.
- `Client.Render()`는 **클라이언트 사본만** 읽는다.
- 1장의 조건(Non-blocking 입력, dt 사용)은 그대로 지킨다.

### 메시지 예시

형식은 자유입니다. 이 정도면 충분합니다.

| 방향 | 이름 | 내용 |
| --- | --- | --- |
| Client → Server | `MoveRequest` | `dx`, `dy` (각각 -1, 0, +1) |
| Server → Client | `StateResponse` | `x`, `y` |

> 이동 속도(초당 칸 수)와 dt는 누가 알아야 할까요? 직접 정해 보고, 왜 그렇게 정했는지 설명할 수 있어야 합니다.
> (힌트: "속도"는 게임 규칙입니다. 게임 규칙의 권위는 누구에게 있나요?)

### 언어

아무 언어나 괜찮습니다. 1장에서 쓴 언어를 그대로 쓰는 것을 추천합니다.

## 직접 구현 순서

코드를 보기 전에 아래 순서대로 직접 만들어 봅니다.

1. **벽 추가**: 1장 게임에 벽을 넣고, 벽에 막히는 것까지 한 프로그램 안에서 먼저 만든다.
2. **Server 클래스**: Game State와 `Update(dt)`, 충돌 검사를 `Server`로 옮긴다.
3. **Client 클래스**: `Input()`과 `Render()`를 `Client`로 옮기고, 사본 좌표를 따로 둔다.
4. **메시지 정의**: `MoveRequest`, `StateResponse`를 만든다.
5. **큐 연결**: `toServer`, `toClient` 큐를 만들고 메시지를 넣고 꺼낸다.
6. **직접 접근 제거**: `Client` 코드에서 `Server`라는 단어가 나오는 곳이 없는지 확인한다.
7. **좌표 두 개 표시**: 서버 좌표와 사본 좌표를 화면에 같이 띄운다.

6번이 가장 중요합니다. 코드에서 검색해 보세요. `Client` 안에서 서버 상태를 읽거나 쓰는 줄이 한 줄이라도 있으면 3장에서 동작하지 않습니다.

막히면 AI에게 **"코드는 주지 말고, 무엇을 찾아보면 되는지만 알려줘"** 라고 물어봅니다.

## 고장 내기

완성한 게임에 일부러 문제를 만들어 봅니다.

| 실험 | 방법 | 관찰할 것 |
| --- | --- | --- |
| 2-1 | 클라이언트가 방향 대신 **위치**(`x`, `y`)를 보내고, 서버는 그 값을 **검증 없이** 그대로 저장한다 | 클라이언트 코드에서 `x += 5`를 하면 벽을 뚫을 수 있는가? |
| 2-2 | 2-1 상태에서 클라이언트가 `x = 9999`를 보낸다 | 서버 상태와 화면은 어떻게 되는가? |
| 2-3 | 클라이언트가 서버 응답을 기다리지 않고 **자기 사본을 먼저 움직이게** 한다. 충돌 검사는 여전히 서버만 한다 | 벽으로 걸어가면 서버 좌표와 사본 좌표는 어떻게 되는가? |
| 2-4 | `toServer` 큐에 넣은 메시지를 **N프레임 뒤에** 꺼내도록 바꾼다 (N = 6, 30) | 키를 누르고 캐릭터가 움직이기까지 느낌이 어떤가? |
| 2-5 | 서버가 `StateResponse`를 **보내지 않게** 한다 | 서버 좌표는 바뀌는가? 화면의 `@`는? |

- **2-1, 2-2**는 "클라이언트가 결과를 정하면" 무슨 일이 생기는지 보는 실험입니다. 15장에서 네트워크 너머로 같은 공격을 해 봅니다.
- **2-3**은 13장 Client Prediction의 맛보기입니다. 반응은 빨라지지만 서버와 어긋나는 순간이 생깁니다.
- **2-4**는 네트워크 지연을 흉내 낸 것입니다. 11장의 장애 시뮬레이터가 이것을 본격적으로 만듭니다.
- **2-5**는 **화면에 보이는 것과 진짜 상태가 다를 수 있다**는 것을 확인하는 실험입니다.

결과는 [부록 B. 실험 기록 양식](../00_index.md#부록-b-실험-기록-양식)에 맞춰 기록합니다.

## 확인 문제

1. 멀티플레이에서 각 클라이언트가 자기 게임 상태를 따로 가지고 결정하면 어떤 문제가 생기는가? 두 가지 이상 말해 보라.
2. 권위(Authority)란 무엇인가? "플레이어 위치의 권위가 서버에 있다"는 말을 설명해 보라.
3. 카메라 각도는 클라이언트가 결정해도 되지만 HP는 안 되는 이유는?
4. 서버가 클라이언트가 보낸 데이터를 믿으면 안 되는 이유는? "클라이언트는 누구의 컴퓨터에서 도는가"를 넣어서 설명하라.
5. 클라이언트가 "내 위치는 x=11"이 아니라 "오른쪽으로 가고 싶다"를 보내는 것이 좋은 이유는?
6. 한 프로그램 안에서도 클라이언트와 서버가 메시지로만 대화하게 만드는 이유는?
7. 서버 권위 방식에서 키를 누른 뒤 캐릭터가 늦게 움직이는 이유는?

5. 결과를 받으면 서버가 어차피 다시 계산해서 확인해야 한다. 의도만 받고 서버가 규칙에 따라 결과를 계산하면 조작할 여지가 줄고 구조도 단순하다.
6. 서버를 다른 컴퓨터로 옮기면 서로의 변수를 직접 건드릴 수 없고 메시지만 보낼 수 있다. 처음부터 메시지로만 대화하게 만들어 두면 나중에 통로만 네트워크로 바꾸면 된다.
7. 입력이 서버까지 가고, 서버가 처리하고, 결과가 다시 돌아와야 화면에 반영되기 때문이다. 왕복 시간만큼 늦어진다.

## 이 장의 핵심 정리

```text
1. 진짜 게임 상태는 하나만 두고, 서버가 가진다. 클라이언트는 사본을 가진다.
2. 권위(Authority) = 최종 결정권. 다른 플레이어에게 영향을 주는 값은 서버가 권위를 가진다.
3. 클라이언트는 플레이어의 손에 있으므로, 서버는 클라이언트가 보낸 것을 믿지 않는다.
4. 클라이언트는 결과가 아니라 의도(요청)를 보내고, 서버가 검증한 뒤 결과(응답)를 정한다.
5. 클라이언트와 서버는 메시지로만 대화한다. 그래야 통로만 네트워크로 바꿀 수 있다.
6. 서버 권위 방식의 대가는 반응 지연이다. (13장에서 해결)
```
