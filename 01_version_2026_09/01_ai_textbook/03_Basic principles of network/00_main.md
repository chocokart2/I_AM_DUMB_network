# 3장. 네트워크의 기본 원리

> 이 장의 질문: **다른 컴퓨터에 있는 프로그램에게 데이터를 보내려면 무엇이 필요한가?**

## 이 장에서 배우는 것

- IP 주소: 어느 **컴퓨터**인가
- Port: 그 컴퓨터의 어느 **프로그램**인가
- Socket: 프로그램이 네트워크를 쓰는 **손잡이**
- 연결(Connection)과 패킷(Packet)
- 송신과 수신: `send`와 `recv`가 실제로 하는 일
- 2장의 메시지 큐와 네트워크는 무엇이 다른가

---

## 3.1 2장 복습: 통로만 바꾸면 된다고 했다

2장에서 클라이언트와 서버를 나누고, 둘이 **메시지 큐로만** 대화하게 만들었습니다.

```text
2장:  클라이언트 ──[ 메모리 안의 큐 ]──→ 서버
3장:  클라이언트 ──[ 네트워크(Socket) ]──→ 서버
```

그리고 "통로만 네트워크로 바꾸면 된다"고 했습니다.
그런데 서버가 **다른 컴퓨터**로 가면, 큐에 넣을 때는 생각하지 않았던 질문들이 생깁니다.

| 질문 | 2장(같은 프로그램)에서는 | 이 장에서 배울 것 |
| --- | --- | --- |
| 상대가 어느 컴퓨터에 있는가? | 같은 컴퓨터라 고민할 필요 없음 | **IP 주소** |
| 그 컴퓨터의 어느 프로그램인가? | 같은 프로그램이라 고민할 필요 없음 | **Port** |
| 무엇을 통해 보내는가? | 큐 변수 | **Socket** |
| 상대가 받을 준비가 됐는가? | 항상 준비돼 있음 | **연결(Connection)** |
| 무엇을 보낼 수 있는가? | 객체(메시지) 그대로 | **바이트(byte)만** |

하나씩 봅시다.

---

## 3.2 IP 주소: 어느 컴퓨터인가

편지를 보내려면 먼저 **집 주소**가 있어야 합니다.
네트워크에서 컴퓨터의 주소가 **IP 주소(IP Address)** 입니다.

```text
192.168.0.15        ← IPv4: 0~255 사이 숫자 4개 (32비트)
fe80::1a2b:3c4d...  ← IPv6: 더 긴 주소 (128비트)
```

IPv4 주소는 약 43억 개뿐이라 부족해져서 IPv6가 만들어졌습니다. 이 교과서는 읽기 쉬운 **IPv4**를 기준으로 설명합니다.

> 정확히 말하면 IP 주소는 컴퓨터가 아니라 **네트워크 장치(랜카드, 와이파이 등)** 에 붙습니다.
> 그래서 한 컴퓨터가 IP 주소를 여러 개 가질 수 있습니다. 지금은 "컴퓨터의 주소"로 생각해도 충분합니다.

### 꼭 알아야 할 특별한 주소

| 주소 | 이름 | 뜻 |
| --- | --- | --- |
| `127.0.0.1` | 루프백(Loopback) | **나 자신.** 이 주소로 보내면 네트워크 밖으로 나가지 않고 내 컴퓨터로 돌아온다 [5] |
| `localhost` | | 보통 `127.0.0.1`(또는 IPv6의 `::1`)을 가리키는 이름 |
| `192.168.x.x`, `10.x.x.x`, `172.16.x.x ~ 172.31.x.x` | 사설 IP(Private IP) | 집이나 회사 **안에서만** 쓰는 주소. 인터넷 너머에서는 이 주소로 찾아올 수 없다 [4] |
| `0.0.0.0` | | 서버가 "기다릴 주소"로 쓸 때: **이 컴퓨터의 모든 주소**에서 받겠다 |

이 장의 예제는 컴퓨터 한 대에서 서버와 클라이언트를 둘 다 띄우므로 **`127.0.0.1`** 을 씁니다.
프로그램은 두 개지만 컴퓨터는 하나입니다. 그래도 두 프로그램은 **진짜 네트워크 코드**로 대화합니다.

> `localhost` 대신 `127.0.0.1`을 직접 쓰는 것을 추천합니다.
> `localhost`는 환경에 따라 IPv6 주소(`::1`)로 먼저 연결을 시도해서, 서버가 IPv4로만 기다리고 있으면 헷갈리는 오류가 날 수 있습니다.

### 내 IP 주소 확인하기

```text
Windows:       ipconfig
macOS / Linux: ip addr  (또는 ifconfig)
```

집에서 확인하면 대부분 `192.168.x.x` 같은 사설 IP가 나옵니다.
같은 공유기에 연결된 다른 컴퓨터에서는 이 주소로 내 서버에 접속할 수 있습니다.

## 3.3 Port: 그 컴퓨터의 어느 프로그램인가

IP 주소로 컴퓨터를 찾았습니다. 그런데 그 컴퓨터에는 브라우저, 메신저, 게임 서버 등 **네트워크를 쓰는 프로그램이 여러 개** 돌고 있습니다.
도착한 데이터를 **어느 프로그램에게** 줘야 할까요?

이걸 구분하는 번호가 **포트(Port)** 입니다.

```text
IP 주소  = 아파트 주소      "행복아파트"
Port     = 호수             "1203호"
```

```text
[ 컴퓨터 192.168.0.15 ]
  ├─ Port 443   → 웹 서버
  ├─ Port 7777  → 내 게임 서버     ← "192.168.0.15의 7777번으로 보내라"
  └─ Port 52341 → 브라우저 (다른 서버에 접속 중)
```

### Port의 규칙

- 0 ~ 65535 사이의 숫자입니다. (16비트)
- **한 컴퓨터에서 같은 포트를 두 프로그램이 동시에 기다릴 수 없습니다.** 이미 쓰고 있으면 "주소가 이미 사용 중(Address already in use)" 오류가 납니다.
- 번호대마다 쓰임새가 정해져 있습니다. [3]

| 범위 | 이름 | 예 |
| --- | --- | --- |
| 0 ~ 1023 | 잘 알려진 포트(System / Well-known) | 80(HTTP), 443(HTTPS), 22(SSH) |
| 1024 ~ 49151 | 등록된 포트(User / Registered) | 게임 서버, DB 등이 주로 사용 |
| 49152 ~ 65535 | 동적 포트(Dynamic / Ephemeral) | OS가 클라이언트에게 자동으로 붙여 줌 |

> 1023 이하 포트는 일부 OS에서 관리자 권한이 있어야 쓸 수 있습니다.
> 이 교과서의 예제는 **7777번**을 씁니다. 특별한 의미는 없고, 겹치지 않을 만한 번호입니다.

### 서버의 포트와 클라이언트의 포트

- **서버**는 포트를 **직접 정합니다.** 클라이언트가 찾아와야 하니까 번호가 정해져 있어야 합니다.
- **클라이언트**도 포트가 있어야 답장을 받을 수 있습니다. 하지만 보통 **직접 정하지 않고 OS가 빈 번호를 아무거나** 붙여 줍니다(위 표의 동적 포트 범위 근처).

```text
클라이언트 127.0.0.1:52341  ──→  서버 127.0.0.1:7777
           ↑ OS가 붙여 줌                     ↑ 서버가 정함
```

`IP:Port` 한 쌍을 **엔드포인트(Endpoint)** 라고 부릅니다. "누구에게"를 정확히 가리키려면 IP와 Port가 **둘 다** 필요합니다.

## 3.4 Socket: 네트워크를 쓰는 손잡이

프로그램은 네트워크 장치를 직접 만지지 않습니다. **운영체제(OS)** 에게 부탁합니다.
이때 OS가 프로그램에게 내어 주는 "네트워크 통로의 손잡이"가 **소켓(Socket)** 입니다. [1]

```text
[ 내 프로그램 ]
     │  send("hello")        ← 소켓에 대고 말한다
     ▼
[ 소켓 ]  ─── OS가 관리 ───  송신 버퍼 / 수신 버퍼
     │
     ▼
[ OS의 네트워크 처리 ] → [ 랜카드 ] → 네트워크 → 상대 컴퓨터
```

파일을 다룰 때 `open`으로 파일을 열고, `read`/`write`로 읽고 쓰고, `close`로 닫는 것과 비슷합니다.
소켓은 **읽고 쓰는 대상이 파일이 아니라 다른 컴퓨터의 프로그램**인 것입니다.

### 서버와 클라이언트는 하는 일이 다르다

전화에 비유하면 서버는 **전화를 받는 쪽**, 클라이언트는 **전화를 거는 쪽**입니다.

```text
[ 서버 ]                                  [ 클라이언트 ]
socket()   소켓 만들기                     socket()   소켓 만들기
bind()     "나는 7777번이다" (번호 받기)
listen()   "전화 받을 준비 됐다"
accept()   전화 올 때까지 기다림  ←─────── connect()  "127.0.0.1:7777에 전화 건다"
   │ (연결 성립)                              │
recv()     듣기               ←───────────── send()     말하기
send()     말하기             ──────────────→ recv()     듣기
   ...                                       ...
close()    끊기                              close()    끊기
```

| 함수 | 누가 | 하는 일 |
| --- | --- | --- |
| `socket()` | 둘 다 | 소켓을 만든다 |
| `bind(IP, Port)` | 서버 | 이 소켓이 쓸 주소와 포트를 정한다 |
| `listen()` | 서버 | 연결 요청을 받을 수 있는 상태로 만든다 |
| `accept()` | 서버 | 연결 요청 하나를 꺼내서 **새 소켓**을 돌려준다 |
| `connect(IP, Port)` | 클라이언트 | 서버에 연결을 요청한다 |
| `send(bytes)` | 둘 다 | 바이트를 보낸다 |
| `recv(최대 크기)` | 둘 다 | 바이트를 받는다 |
| `close()` | 둘 다 | 연결을 끊고 소켓을 돌려준다 |

이 이름들은 C 언어의 **버클리 소켓(Berkeley Sockets)** API에서 왔고, 대부분의 언어가 비슷한 이름을 씁니다. [1]

| 개념 | Python | C# |
| --- | --- | --- |
| 소켓 만들기 | `socket.socket()` | `new Socket(...)` 또는 `TcpListener` / `TcpClient` |
| bind / listen | `bind()`, `listen()` | `Bind()`, `Listen()` |
| accept | `accept()` | `Accept()` |
| connect | `connect()` | `Connect()` |
| send | `send()` / `sendall()` | `Send()` |
| recv | `recv()` | `Receive()` |

### 중요: `accept()`는 새 소켓을 돌려준다

서버에는 소켓이 **두 종류** 있습니다. 헷갈리기 쉬운 부분입니다.

```text
[ 서버 ]
  리슨 소켓(Listening Socket) :7777   ← 문지기. 새 손님만 받는다. 데이터는 안 주고받는다.
       │ accept()
       ├──→ 연결 소켓 #1  ↔  클라이언트 A     ← 실제 대화는 여기서
       └──→ 연결 소켓 #2  ↔  클라이언트 B
```

- **리슨 소켓**은 하나입니다. 7777번에서 "새 연결 요청"만 기다립니다.
- `accept()`가 연결 하나를 받을 때마다 **그 클라이언트 전용 소켓**이 새로 생깁니다.
- `send`/`recv`는 **연결 소켓**으로 합니다.

그래서 서버 하나가 7777번 포트 하나로 여러 클라이언트와 대화할 수 있습니다. 여러 명을 **동시에** 다루는 방법은 5장에서 배웁니다. 이 장에서는 한 번에 한 명만 받습니다.

## 3.5 연결(Connection)

이 장에서 쓰는 방식은 **TCP**입니다. TCP는 데이터를 주고받기 전에 먼저 **연결**을 맺습니다. [2]

```text
클라이언트                    서버
   │ ── "연결하고 싶다" ──→      │   (SYN)
   │ ←─ "좋다, 너도 준비됐나?" ── │   (SYN + ACK)
   │ ── "준비됐다" ──→           │   (ACK)
   │ ====== 연결 성립 ======     │
```

이 세 번의 주고받기를 **3-way handshake** 라고 합니다. `connect()`와 `accept()` 안에서 OS가 알아서 해 주므로 직접 코드로 짤 일은 없습니다.
지금은 "**연결은 저절로 생기지 않고, 양쪽이 합의해야 생긴다**"는 것만 기억합니다.

### 연결은 네 가지 값으로 구분된다

서버 입장에서 연결 소켓 #1과 #2는 어떻게 구분될까요? 둘 다 서버의 7777번인데요.

```text
연결 = (내 IP, 내 Port, 상대 IP, 상대 Port)

연결 #1: (127.0.0.1, 7777, 127.0.0.1, 52341)
연결 #2: (127.0.0.1, 7777, 127.0.0.1, 52388)   ← 상대 Port가 다르다
```

네 값 중 하나라도 다르면 다른 연결입니다. [2]
클라이언트 포트를 OS가 매번 다르게 붙여 주는 덕분에, 같은 컴퓨터에서 클라이언트를 여러 개 띄워도 서로 섞이지 않습니다.

> 이 "누구와의 연결인가"라는 개념이 5장의 **Session**, 20장의 재접속 처리로 이어집니다.

### 연결이 끊어지는 것을 어떻게 아는가

상대가 `close()`하면, 내 쪽 `recv()`가 **0바이트**를 돌려줍니다. [1][7]

```text
recv() 결과 > 0   → 데이터가 왔다
recv() 결과 = 0   → 상대가 연결을 정상적으로 끊었다
recv() 에서 오류  → 연결이 비정상적으로 끊겼다 (상대 프로그램이 죽음 등)
```

"0바이트 = 끊김"이라는 규칙을 모르면, 끊긴 연결에서 무한히 `recv()`를 반복하는 버그가 생깁니다.

## 3.6 패킷(Packet)

`send("hello")`를 하면 "hello"가 한 덩어리로 날아갈 것 같지만, 실제로는 **포장**이 여러 겹 붙은 채로 갑니다.

```text
내가 보낸 데이터:                         [ hello ]
TCP가 붙이는 것 (포트, 순서 번호 등):  [TCP 헤더][ hello ]
IP가 붙이는 것 (IP 주소 등):     [IP 헤더][TCP 헤더][ hello ]
랜카드/와이파이가 붙이는 것: [...][IP 헤더][TCP 헤더][ hello ][...]
```

편지를 봉투에 넣고, 그 봉투를 다시 택배 상자에 넣는 것과 같습니다.
각 층은 **자기 포장만** 보고 처리합니다. 이 구조를 **계층(Layer)** 이라고 합니다.

| 계층 | 하는 일 | 보는 정보 |
| --- | --- | --- |
| 애플리케이션 (내 프로그램) | 무엇을 보낼지 정한다 | "hello" |
| 전송 (TCP / UDP) | 어느 **프로그램**에게, 어떻게 보낼지 | Port |
| 인터넷 (IP) | 어느 **컴퓨터**에게 보낼지 | IP 주소 |
| 링크 (이더넷, 와이파이) | 바로 옆 장치까지 전달 | 하드웨어 주소 |

그리고 네트워크는 한 번에 보낼 수 있는 크기에 한계가 있습니다(이더넷은 보통 약 1500바이트).
그래서 큰 데이터는 **잘게 나뉘어** 가고, 받는 쪽에서 다시 이어 붙입니다. 이렇게 네트워크를 실제로 지나가는 한 조각을 **패킷(Packet)** 이라고 합니다.

### "패킷"이라는 말은 두 가지로 쓰인다

| | 네트워크의 패킷 | 게임의 패킷 |
| --- | --- | --- |
| 뜻 | 네트워크를 지나가는 데이터 한 조각 | 게임이 정한 메시지 하나 (`C_LOGIN`, `MoveRequest` 등) |
| 누가 정하는가 | OS와 네트워크 장비 | **내가** 정한다 |
| 크기 | 네트워크 한계에 따라 나뉨 | 내가 정한 형식대로 |
| 나오는 곳 | 이 장, 4장 | 7장 이후 |

게임 개발에서 "패킷"이라고 하면 보통 **게임의 패킷(메시지)** 을 말합니다.
문제는 **게임 메시지 하나가 네트워크 패킷 하나와 딱 맞지 않는다**는 것입니다. 이게 3.7의 핵심입니다.

> 정확한 용어로는 TCP의 조각은 세그먼트(Segment), UDP는 데이터그램(Datagram), IP는 패킷이라고 부릅니다. 이 교과서에서는 구분이 필요할 때만 나눠 씁니다.

## 3.7 송신과 수신

소켓 코드를 처음 짤 때 가장 많이 틀리는 곳입니다. 네 가지를 기억합니다.

### 1. 보낼 수 있는 것은 바이트뿐이다

소켓은 **바이트 배열**만 보냅니다. 문자열도, 숫자도, 객체도 바로 보낼 수 없습니다.

```text
"hello"  ──(UTF-8 인코딩)──→  68 65 6C 6C 6F        (5바이트)
"안녕"    ──(UTF-8 인코딩)──→  EC 95 88 EB 85 95     (6바이트, 한글은 글자당 3바이트)
```

- 보낼 때: 문자열 → 바이트 (**인코딩**)
- 받을 때: 바이트 → 문자열 (**디코딩**)
- 양쪽이 **같은 인코딩**을 써야 합니다. 이 교과서는 **UTF-8**을 씁니다.

2장의 `MoveRequest { dx = 1, dy = 0 }` 같은 메시지를 바이트로 바꾸는 방법(**직렬화**)은 7장에서 배웁니다.
2장에서 "메시지에는 순수한 데이터만 담는다"고 한 이유가 이것입니다. 포인터나 객체 참조는 바이트로 바꿔서 다른 컴퓨터로 보내도 의미가 없습니다.

### 2. `send()`는 "도착했다"가 아니라 "맡겼다"이다

```text
send("hello") 가 성공했다
   = OS의 송신 버퍼에 "hello"를 넣었다      ← O
   ≠ 상대 프로그램이 "hello"를 받았다        ← X
```

`send()`는 데이터를 OS에게 맡기고 바로 돌아옵니다. 실제 전송은 OS가 뒤에서 합니다.
상대가 받았는지 확실히 알고 싶으면 **상대가 "받았다"고 답장**을 보내야 합니다. (13장의 Ack가 이 아이디어입니다.)

또 `send()`는 **보낸 바이트 수**를 돌려줍니다. 버퍼가 꽉 차면 일부만 맡기고 돌아올 수도 있습니다. [1][7]
Python의 `sendall()`처럼 "전부 보낼 때까지 반복해 주는" 함수를 쓰거나, 반환값을 확인해서 남은 부분을 다시 보내야 합니다.

### 3. `recv()`는 기다린다 (Blocking)

```text
recv() 호출
   ↓
수신 버퍼에 데이터가 있나?
   ├─ 있다 → 있는 만큼(최대 크기까지) 꺼내서 돌려준다
   └─ 없다 → 올 때까지 여기서 멈춘다   ← !!
```

기본 소켓은 `recv()`, `accept()`에서 **데이터(또는 연결)가 올 때까지 프로그램이 멈춥니다.** 이것을 **Blocking** 이라고 합니다.

1장에서 이런 말을 했습니다.

> 입력을 **기다리면** 게임이 멈춘다.

`recv()`도 똑같습니다. 게임 루프 안에서 `recv()`를 그냥 부르면, 서버가 답장을 보낼 때까지 **화면도 입력도 멈춥니다.**
이 장의 예제(Echo)는 멈춰도 상관없는 프로그램이라 Blocking으로 만듭니다. 게임 루프와 함께 쓰는 방법(Non-blocking, Thread, Event Loop)은 **5장**에서 배웁니다.

### 4. TCP는 "메시지"가 아니라 "바이트의 흐름"이다

**이 장에서 가장 중요한 내용입니다.**

2장의 큐는 메시지를 **한 개씩** 넣고 **한 개씩** 꺼냈습니다. 넣은 것과 꺼낸 것의 **경계가 똑같았습니다.**
TCP는 그렇지 않습니다. TCP는 **순서대로 이어진 바이트의 흐름(Stream)** 만 보장합니다. [2][7]

```text
보내는 쪽:  send("AB")   send("CD")   send("EF")

받는 쪽이 받을 수 있는 모양 (전부 가능):
  recv → "ABCDEF"                        ← 세 번 보낸 게 한 번에 옴
  recv → "A",  recv → "BCDE", recv → "F" ← 보낸 것과 상관없이 나뉘어 옴
  recv → "AB", recv → "CD",   recv → "EF"  ← 우연히 맞게 옴
```

TCP가 보장하는 것은 이것뿐입니다.

- **순서**: A 다음에 B가 온다. 순서가 뒤바뀌지 않는다.
- **빠짐없이**: 중간이 빠지지 않는다. (빠지면 TCP가 알아서 다시 보낸다. 4장)

보장하지 **않는** 것:

- **`send` 한 번 = `recv` 한 번**이 아니다. 메시지의 경계가 보존되지 않는다.

비유하면 TCP는 **파이프에 물을 흘려보내는 것**과 같습니다. 컵으로 세 번 부어도 받는 쪽에는 "물의 흐름"만 도착하지, "컵 세 개"가 도착하지 않습니다.

그래서 받는 쪽이 **"어디까지가 메시지 하나인지"** 를 직접 알아내야 합니다. 방법은 크게 두 가지입니다.

| 방법 | 예 | 나오는 곳 |
| --- | --- | --- |
| 구분자(Delimiter) 넣기 | 메시지 끝에 줄바꿈 `\n`을 붙인다 | 5장 채팅 |
| 길이를 먼저 보내기 | 앞에 "이 메시지는 12바이트다"를 붙인다 | 7장 Packet Size |

이 장의 Echo 예제에서는 **"보낸 바이트 수만큼 돌아올 때까지 받는다"** 는 간단한 방법을 씁니다. Echo는 보낸 것이 그대로 돌아오므로 몇 바이트를 기다려야 하는지 알 수 있기 때문입니다.

## 3.8 2장의 큐와 소켓 비교

이제 2장의 `Pipe`(메시지 큐)를 소켓으로 바로 바꿀 수 없는 이유가 보입니다.

| | 2장 메시지 큐 | TCP 소켓 |
| --- | --- | --- |
| 상대 위치 | 같은 프로그램 | 다른 프로그램 (다른 컴퓨터일 수도) |
| 찾아가는 법 | 변수 | IP + Port |
| 보내는 것 | 메시지 객체 | **바이트** |
| 경계 | 메시지 하나씩 | **경계 없음 (스트림)** |
| 도착 시간 | 즉시 | 지연 있음 |
| 받기 | 없으면 그냥 지나감 | 기본은 **기다림 (Blocking)** |
| 실패 | 없음 | 연결 실패, 끊김, 상대 종료 |

그래서 2장 게임을 네트워크로 옮기려면 세 가지가 더 필요합니다.

1. 메시지 ↔ 바이트 변환 (**직렬화**) — 7장
2. 바이트 흐름에서 메시지 하나씩 잘라내기 (**메시지 경계**) — 5장, 7장
3. 게임 루프를 멈추지 않고 받기 (**Non-blocking / Thread**) — 5장

이 장에서는 그 전에, **두 프로그램이 네트워크로 바이트를 주고받는 가장 단순한 상황**을 직접 만들어 봅니다.

## 3.9 눈으로 확인하는 도구

소켓은 코드 안에서는 보이지 않지만, OS에게 물어보면 지금 어떤 연결이 있는지 볼 수 있습니다.

```text
Windows (PowerShell):
  netstat -ano | findstr 7777
  Get-NetTCPConnection -LocalPort 7777

macOS / Linux:
  netstat -an | grep 7777
  ss -tan | grep 7777        (Linux)
```

예제를 실행한 채로 확인하면 이런 상태들이 보입니다.

| 상태 | 뜻 |
| --- | --- |
| `LISTEN` / `Listen` | 리슨 소켓이 연결을 기다리는 중 |
| `ESTABLISHED` / `Established` | 연결이 맺어져 대화 중 |
| `TIME_WAIT` / `TimeWait` | 연결을 끊은 직후 잠깐 남아 있는 상태 |

연결 하나에 줄이 **두 개** 보일 것입니다. 같은 컴퓨터 안이라 서버 쪽 소켓과 클라이언트 쪽 소켓이 둘 다 보이기 때문입니다. 3.5의 네 가지 값을 직접 확인해 보세요.

## 예제 3 — TCP Echo Server

> AI 예제 위치: `02_ai_example`
> 내 구현 위치: `03_human_example`

**Echo Server**는 받은 것을 그대로 돌려보내는 서버입니다. 게임 규칙이 전혀 없어서 네트워크 코드만 볼 수 있습니다.

```text
클라이언트: "hello"  ──→  서버
클라이언트: "hello"  ←──  서버 (그대로 돌려줌)
```

### 요구사항

**서버 프로그램**

1. `0.0.0.0:7777`에서 연결을 기다린다. 포트는 실행 옵션으로 바꿀 수 있다.
2. 클라이언트가 연결하면, 받은 바이트를 **그대로** 돌려보낸다.
3. 클라이언트가 연결을 끊으면(`recv` = 0) 로그를 남기고, **다음 클라이언트를 기다린다.** (서버는 꺼지지 않는다)
4. 한 번에 **한 명만** 상대한다. (여러 명은 5장)
5. 모든 일을 로그로 출력한다: 기다리기 시작, 연결 수락(상대 엔드포인트), 받은 바이트 수와 내용, 보낸 바이트 수, 연결 종료.

**클라이언트 프로그램**

1. `127.0.0.1:7777`에 연결한다. 주소와 포트는 실행 옵션으로 바꿀 수 있다.
2. 연결되면 **내 엔드포인트**(OS가 붙여 준 포트)를 출력한다.
3. 키보드로 한 줄을 입력받아 UTF-8 바이트로 바꿔 보낸다.
4. **보낸 바이트 수만큼 다 받을 때까지** `recv`를 반복한 뒤, 문자열로 바꿔 출력한다.
5. `/quit`을 입력하면 연결을 끊고 종료한다.
6. 서버가 먼저 끊으면 그 사실을 출력하고 종료한다.

**서버와 클라이언트는 별도의 프로그램(별도의 프로세스)** 으로 만듭니다. 터미널 두 개를 열어 각각 실행합니다.

```text
[ 터미널 1: 서버 ]
[Server] Listening on 0.0.0.0:7777
[Server] Accepted 127.0.0.1:52341
[Server] Recv 5 bytes from 127.0.0.1:52341: "hello"
[Server] Sent 5 bytes
[Server] Recv 6 bytes from 127.0.0.1:52341: "안녕"
[Server] Sent 6 bytes
[Server] 127.0.0.1:52341 disconnected
[Server] Listening on 0.0.0.0:7777

[ 터미널 2: 클라이언트 ]
[Client] Connecting to 127.0.0.1:7777 ...
[Client] Connected. Local endpoint = 127.0.0.1:52341
> hello
[Client] Sent 5 bytes
[Client] Echo (5 bytes): "hello"
> 안녕
[Client] Sent 6 bytes
[Client] Echo (6 bytes): "안녕"
> /quit
[Client] Bye
```

### 구조 조건

- 서버에서 **리슨 소켓과 연결 소켓을 구분**해서 변수 이름을 짓는다. (예: `listener`, `conn`)
- `recv`의 반환값이 **0이면 연결 종료**로 처리한다.
- `send`는 **전부 보내졌는지** 확인한다. (반환값 확인, 또는 `sendall` 같은 함수 사용)
- 클라이언트는 `recv` 한 번에 전부 올 거라고 **가정하지 않는다.** 받은 바이트를 모았다가 다 모이면 디코딩한다.
- 서버의 수신 버퍼 크기(`recv`에 넘기는 최대 크기)는 실행 옵션으로 바꿀 수 있게 한다. (고장 내기 3-7에서 쓴다)
- 연결 실패, 상대의 비정상 종료 같은 **오류가 나도 프로그램이 알 수 없는 예외로 죽지 않고**, 무슨 일이 있었는지 출력한다.

### 언어

아무 언어나 괜찮습니다. 표준 라이브러리의 소켓만 사용하고, 네트워크 라이브러리나 프레임워크는 쓰지 않습니다.
C#이라면 `TcpListener`/`TcpClient`보다 `Socket` 클래스를 직접 쓰는 것을 추천합니다. `bind`, `listen`, `accept`가 코드에 그대로 드러나기 때문입니다.

## 직접 구현 순서

코드를 보기 전에 아래 순서대로 직접 만들어 봅니다.

1. **서버: 기다리기만 하기**: `socket → bind → listen → accept`까지만 만든다. 서버를 켜고 3.9의 도구로 `LISTEN`이 보이는지 확인한다.
2. **클라이언트: 연결만 하기**: `socket → connect`까지만 만든다. 연결되면 서버가 수락 로그를 찍는지, `ESTABLISHED`가 보이는지 확인한다.
3. **한 번 주고받기**: 클라이언트가 "hello"를 한 번 보내고, 서버가 받아서 출력하고 돌려보내고, 클라이언트가 출력한다.
4. **반복하기**: 클라이언트는 입력을 반복해서 받고, 서버는 `recv`를 반복한다.
5. **끊기 처리**: `/quit`과 `recv = 0`을 처리한다. 클라이언트가 끊은 뒤 서버가 다음 클라이언트를 기다리는지 확인한다.
6. **바이트 수 맞추기**: 클라이언트가 보낸 바이트 수만큼 다 받을 때까지 모으게 한다.
7. **오류 처리**: 서버 없이 클라이언트를 켰을 때, 도중에 서버를 강제 종료했을 때 메시지를 출력하게 한다.

1, 2번에서 **데이터를 하나도 안 보냈는데도 연결은 생긴다**는 것을 꼭 확인하세요. 연결과 데이터 전송은 별개의 단계입니다.

막히면 AI에게 **"코드는 주지 말고, 무엇을 찾아보면 되는지만 알려줘"** 라고 물어봅니다.

## 고장 내기

완성한 프로그램에 일부러 문제를 만들어 봅니다. 각 실험 전에 **결과를 먼저 추측**해서 적어 두세요.

| 실험 | 방법 | 관찰할 것 |
| --- | --- | --- |
| 3-1 | 서버를 켜지 않고 클라이언트만 실행한다 | 어떤 오류가 나는가? 바로 나는가, 한참 뒤에 나는가? |
| 3-2 | 서버를 켠 채로, 같은 포트로 서버를 **하나 더** 실행한다 | 두 번째 서버는 어떻게 되는가? |
| 3-3 | 클라이언트 A가 연결된 상태에서 클라이언트 B를 하나 더 실행하고 메시지를 보낸다 | B의 `connect`는 성공하는가? B의 메시지에 답이 오는가? A가 `/quit`하면 B는 어떻게 되는가? |
| 3-4 | 대화 중에 서버 창을 강제로 닫는다 (Ctrl+C 등) | 클라이언트가 다음 메시지를 보내거나 받을 때 무슨 일이 생기는가? |
| 3-5 | 서버가 `recv` 후 돌려보내기 전에 **3초 기다리게** 한다 | 그동안 클라이언트는 무엇을 할 수 있는가? |
| 3-6 | 클라이언트가 `"AB"`, `"CD"`, `"EF"`를 **연달아 세 번** `send`하고, 서버는 매 `recv` 전에 **1초 기다리게** 한다 | 서버는 `recv`를 몇 번 하고, 한 번에 무엇을 받는가? |
| 3-7 | 서버의 수신 버퍼 크기를 **4바이트**로 줄이고 `"안녕하세요"`를 보낸다 | 서버 로그는 어떻게 찍히는가? 클라이언트에는 제대로 돌아오는가? |
| 3-8 | 서버를 `0.0.0.0` 대신 `127.0.0.1`로 bind한다. 같은 공유기의 다른 기기(다른 PC 등)에서 내 사설 IP로 접속해 본다 | `0.0.0.0`일 때와 무엇이 다른가? |

- **3-1**은 "그 포트에서 기다리는 프로그램이 없다"는 뜻의 **연결 거부(Connection refused)** 입니다. 주소는 맞는데 받을 사람이 없는 것입니다.
- **3-2**는 3.3의 "한 포트를 두 프로그램이 동시에 기다릴 수 없다"를 확인하는 실험입니다.
- **3-3**의 결과는 의외일 수 있습니다. 서버가 `accept`를 하지 않았는데도 B의 `connect`는 **성공**합니다. OS가 연결을 대신 받아서 **대기열(backlog)** 에 넣어 두기 때문입니다. [6] 하지만 서버 코드가 아직 B의 소켓을 꺼내지 않았으니, B의 메시지는 버퍼에 쌓이기만 하고 답이 없습니다. 5장의 문제 제기입니다.
- **3-4**는 3.5의 "비정상적으로 끊긴 연결"입니다. 상대가 사라져도 **내가 뭔가를 보내거나 받기 전까지는 모를 수 있다**는 점을 확인하세요.
- **3-5**는 Blocking의 체감입니다. 게임이었다면 3초 동안 화면이 멈춘 것입니다.
- **3-6**은 3.7의 "TCP는 스트림이다"를 눈으로 보는 실험입니다. 세 번 보냈는데 한 번에 `"ABCDEF"`가 올 수 있습니다. (항상 그렇지는 않습니다. 여러 번 해 보세요.)
- **3-7**은 반대 방향입니다. 한 번 보낸 것이 여러 번 나뉘어 옵니다. 한글은 글자당 3바이트라서, 4바이트씩 잘린 조각을 **따로따로 디코딩하면 글자가 깨집니다.** 그런데 클라이언트는 바이트를 **다 모은 뒤** 디코딩하므로 제대로 보일 것입니다. **"다 모으고 나서 해석한다"** 가 7장 패킷 처리의 기본 원칙이 됩니다.
- **3-8**은 bind 주소의 의미를 확인하는 실험입니다. 방화벽이 막을 수 있으니, 안 되면 방화벽 허용 여부부터 확인하세요. 다른 기기가 없으면 건너뛰어도 됩니다.

결과는 [부록 B. 실험 기록 양식](../00_index.md#부록-b-실험-기록-양식)에 맞춰 기록합니다.

## 확인 문제

1. IP 주소와 Port는 각각 무엇을 구분하는가? 둘 중 하나만 있으면 안 되는 이유는?
2. `127.0.0.1`과 `0.0.0.0`은 각각 무엇을 뜻하는가? 서버가 bind할 때 둘은 어떻게 다른가?
3. 서버는 포트 번호를 직접 정하는데, 클라이언트는 보통 정하지 않는 이유는?
4. 서버에서 리슨 소켓과 `accept()`가 돌려준 소켓은 각각 무슨 일을 하는가?
5. 서버의 7777번 포트에 클라이언트 두 개가 연결되어 있을 때, 서버는 두 연결을 어떻게 구분하는가?
6. `send()`가 성공적으로 돌아왔다면, 상대가 데이터를 받았다고 말할 수 있는가?
7. `recv()`가 0을 돌려주면 무슨 뜻인가?
8. 클라이언트가 `send("AB")`, `send("CD")`를 했다. 서버의 첫 `recv()`가 `"AB"`를 돌려줄 것이라고 가정하면 안 되는 이유는?
9. 게임 루프 안에서 Blocking `recv()`를 그냥 부르면 어떻게 되는가?
10. 2장의 메시지 큐를 TCP 소켓으로 바로 바꿀 수 없는 이유를 세 가지 말해 보라.

<details>
<summary>답 보기</summary>

1. IP 주소는 어느 컴퓨터(네트워크 장치)인지, Port는 그 컴퓨터 안의 어느 프로그램인지 구분한다. IP만 있으면 컴퓨터는 찾아도 어느 프로그램에 줄지 모르고, Port만 있으면 어느 컴퓨터로 가야 할지 모른다.
2. `127.0.0.1`은 나 자신(루프백)이고, `0.0.0.0`은 bind할 때 "이 컴퓨터의 모든 주소"를 뜻한다. `127.0.0.1`로 bind하면 같은 컴퓨터 안에서만 접속할 수 있고, `0.0.0.0`으로 bind하면 다른 컴퓨터에서도 이 컴퓨터의 IP로 접속할 수 있다.
3. 서버는 클라이언트가 찾아와야 하므로 번호가 미리 정해져 있어야 한다. 클라이언트는 누가 찾아올 일이 없고, 답장만 받으면 되므로 OS가 붙여 주는 빈 번호로 충분하다. 직접 정하면 같은 컴퓨터에서 클라이언트를 여러 개 띄울 때 번호가 겹친다.
4. 리슨 소켓은 새 연결 요청을 받기만 한다. `accept()`가 돌려준 연결 소켓은 특정 클라이언트 한 명과 실제로 데이터를 주고받는다.
5. (내 IP, 내 Port, 상대 IP, 상대 Port) 네 가지 값으로 구분한다. 서버 쪽 값은 같아도 클라이언트의 Port가 다르므로 서로 다른 연결이다.
6. 없다. `send()` 성공은 OS의 송신 버퍼에 데이터를 맡겼다는 뜻일 뿐이다. 받았는지 알려면 상대가 답장을 보내야 한다.
7. 상대가 연결을 정상적으로 끊었다는 뜻이다.
8. TCP는 바이트의 흐름만 보장하고 `send` 단위의 경계를 보존하지 않는다. `"ABCD"`가 한 번에 올 수도 있고, `"A"`, `"BCD"`처럼 나뉘어 올 수도 있다.
9. 데이터가 올 때까지 게임 루프 전체가 멈춘다. 입력도, Update도, 화면도 멈춘다.
10. (1) 소켓은 메시지 객체가 아니라 바이트만 보낼 수 있다(직렬화 필요). (2) TCP는 메시지 경계를 보존하지 않는다(메시지를 잘라낼 방법 필요). (3) 기본 `recv()`는 Blocking이라 게임 루프를 멈춘다(Non-blocking 등 필요). 그 밖에 지연이 생기고, 연결이 끊기는 실패를 처리해야 한다.

</details>

## 이 장의 핵심 정리

```text
1. IP 주소는 컴퓨터를, Port는 그 컴퓨터 안의 프로그램을 가리킨다. 둘을 합친 것이 엔드포인트다.
2. Socket은 OS가 주는 네트워크 통로의 손잡이다.
3. 서버: socket → bind → listen → accept.  클라이언트: socket → connect.
4. 리슨 소켓은 연결을 받기만 하고, accept가 돌려준 소켓으로 대화한다.
5. TCP 연결은 (내 IP, 내 Port, 상대 IP, 상대 Port)로 구분된다.
6. 소켓은 바이트만 보낸다. send 성공은 "도착"이 아니라 "OS에 맡김"이다.
7. recv는 기본적으로 기다린다(Blocking). 0을 받으면 상대가 끊은 것이다.
8. TCP는 메시지가 아니라 바이트의 흐름이다. 메시지 경계는 내가 직접 만들어야 한다.
```

## 다음 장 예고

이 장에서는 **TCP**만 썼습니다. TCP는 순서를 지키고 빠진 데이터를 다시 보내 줍니다. 편리하지만 공짜는 아닙니다.
4장에서는 또 다른 방식인 **UDP**를 배웁니다. UDP는 연결도 없고, 순서도, 도착도 보장하지 않습니다. 그런데도 많은 실시간 게임이 UDP를 씁니다. 왜 그런지, TCP 채팅과 UDP 위치 전송을 직접 비교하며 알아봅니다.
